# 需求整理：客服与智能体合并、工具自主判断、实时数据口径、用户记忆、仪表盘（2026-11-23）

来源：用户在对话里的反馈原话，由 Claude 整理。后端、数据结构和技术方案由 Codex 决定；本文只写目标与边界。

## 1. AI 客服 = 智能体，性格并入人设

用户原话要点：
- “客服就是智能体，这两个完全没必要分开。”
- “性格其实就是通用设置里的人设和风格。”
- “不同机器人不同群聊，它是不同的网站……这个 AI 客服负责的是网站 A，另一个 AI 客服负责的是网站 B，所以我是想让你在 AI 客服里去把这一部分拿出来，可以进行不同的修改，结果你把它都放到通用里了。”

目标：
- 去掉“智能体”和“性格”两个独立概念，只保留 **AI 客服**。一个 AI 客服自带：名称、人设与说话风格、示例对话、职责说明、对话模型 / 辅助模型 / 群消息判断模型。
- 以下内容从“通用设置”移到 **每个 AI 客服自己** 下面，可分别配置：
  - 网站实时数据（网站地址、令牌、用户 ID、刷新、公告同步、报价说明、状态页）
  - 技能与工具（启用哪些、最多几轮）
  - 学习与转人工（质检、从官方客服学习、自动发布、候选知识发布到哪个知识库、转人工安静时长）
  - 知识库范围（如果后端可以按客服区分）
- “通用设置”只留真正全局的东西：回复长度与格式、上下文预算、记忆开关等默认值。可由 Codex 判断哪些更适合放在客服级。
- 现有数据迁移：现有“智能体 + 性格 + 通用人设 + 通用实时数据”要无损合并到现有 AI 客服里，不能让线上群停止回复。

## 2. AI 工具

- 缺一个工具：**把 HTML 发布成公网链接**（临时网页），现在只有“HTML 排版成图片”。
- 生成图片 / 网页要 **由 AI 自己判断** 是否调用：
  - 要说的内容很多、一两句说不清时，主动生成网页或图片；
  - 想强调某些信息时，也可以用图片强调；
  - 总体上更倾向生成网页。
- 这是提示词与工具描述层面的引导，不是用户点名才调用。

## 3. 网站实时数据口径

- 网站报价是 **美元**。
- 用户 **用英文提问 → 回复美元**；**用中文提问 → 换算成人民币，按 1 美元 = 7 元**。
- **用户实际价格 = 基础价格 × 分组倍率**。所有对用户说出的价格都必须是乘过倍率之后的价格，回答时说清是哪个分组。
- 分组状态：现在用的是从网站接口监听的数据。用户另有一个 **单独做的状态页面**，问到分组/服务状态时，**把那个页面截图发给用户**。
  - 状态页地址需要问用户，仓库里没找到；做成每个 AI 客服可配置的“状态页地址”。

## 4. 403 内容违规导致整群不回复

用户原话要点：上游审核返回 403 说明内容违规；因为带上下文，违规内容一直在上下文里，整个群之后都不回复了。

目标：出现 403 时，本次新增的那条消息视为违规消息，从后续上下文里剔除，不能让整个会话卡死。

现状：`backend/internal/app/workers.go` 的 `excludeModeratedMessage` 已经对“主对话调用 403”做了剔除。请 Codex 核实：
- 群消息判断模型、问题改写、摘要、记忆提取等其他调用遇到 403 是否也走剔除；
- 违规内容已被写进会话摘要的情况；
- 线上版本是否已包含该修复。

## 5. 公网基础地址放到后台配置

- 临时网页用的公网基础地址，现在写在环境变量 `PUBLIC_BASE_URL`，要改为 **在管理后台网页里配置**（系统状态或管理员页）。
- 这个地址和机器人绑定时的 **回调地址** 是同一个域名，应放在一起配置；机器人页“复制回调地址”也用这个配置。环境变量可作为首次默认值。

## 6. 用户记忆（三层）

用户设想 + 业界方案对照：

| 层 | 用户设想 | 业界对应 |
| --- | --- | --- |
| 用户档案 | 每个用户一份画像（性别、性格、身份、偏好等），AI 每次对话后总结并改写，上限约 2000 token | Letta/MemGPT 的 core memory block、ChatGPT 的“记忆摘要”、LangMem 的 profile |
| 事件记忆 | 用户很早之前说过/做过的具体事（“他 199x 年做过什么”） | Mem0 的结构化事实、ChatGPT 的“已保存记忆”、LangMem 的 episodic/semantic memory；按相似度召回 |
| 近期上下文 | 最近的聊天内容 | 短期上下文 / 摘要 |

建议从业界借鉴的点（供 Codex 取舍）：
- 档案每次 **整体改写** 而不是追加，始终限制在 ~2000 token；回复时固定带入。
- 事件记忆写入时做 **新增 / 更新 / 删除 / 不变** 判断（Mem0 做法），避免同一件事存多条或互相矛盾；每条记下时间（Zep 的时间维度），便于说“你上个月提过……”。
- 提取在 **回复之后异步** 进行，不拖慢回复。
- 不记录密钥、密码、手机号等敏感信息；管理员可以查看、修改、删除档案和每条记忆。
- 前端“用户记忆”页需要同时展示：档案（可编辑）+ 事件记忆列表。

## 7. 前端：去掉多余说明

- 不要加很多额外说明文字，例如首页“点开直接处理”这类注释。各页面的说明性副标题同样精简。

## 8. 首页（今日概览）关注点

按用户顺序：
1. 整体任务处理状态（排队、处理中、失败）
2. 处理了多少消息
3. 知识库丰富到什么程度（文档数、知识问答数、已索引比例等）
4. 消息处理流程每个环节的平均用时，一眼看出哪里慢
5. 最新动态：最近几条回复；当前空闲还是正在回复；**正在回复时显示哪个机器人在哪个群、回复谁、什么问题**

第 5 点“正在回复”需要后端提供“当前处理中的任务”数据（机器人、群、提问人、问题、所在环节）。
